# Deployment

Pi Web supports Linux systemd user services and a self-contained Docker
Compose deployment. Both approaches run as an ordinary user and keep runtime
state outside the repository.

## Credentials

Keep these three credentials separate:

1. The Pi Web access key authenticates the browser. Only its scrypt hash is
   stored.
2. Provider credentials belong to Pi and must be configured for the same
   operating-system or container user.
3. Scheduler worker tokens are short-lived internal credentials generated by
   Pi Web. Operators do not create or persist them.

Do not place real credentials in `.env.example`, screenshots, logs, issues, or
commits.

## Linux user services

From a release checkout:

```bash
pnpm install --frozen-lockfile
pnpm build
pnpm pi-web install
pnpm pi-web doctor
```

The installer writes:

- `~/.config/pi-web/config.json`
- `~/.local/share/pi-web/pi-web.sqlite`
- `~/.local/share/pi-web/sessiond.sock`
- `~/.config/systemd/user/pi-web-sessiond.service`
- `~/.config/systemd/user/pi-web-server.service`

It never runs `sudo`. An administrator may enable lingering if the user
services must survive logout:

```bash
loginctl enable-linger "$USER"
```

Useful commands:

```bash
pnpm pi-web status
pnpm pi-web doctor
pnpm pi-web set-password
pnpm pi-web reset-key
pnpm pi-web uninstall
```

`uninstall` removes service units but preserves configuration, databases,
schedules, and Pi session references.

## Docker Compose

POSIX shell:

```bash
cp .env.docker.example .env
mkdir -p .runtime/docker/data .runtime/docker/pi workspaces
docker compose build
docker compose run --rm pi-web node dist/index.js set-password
docker compose run --rm --entrypoint pi pi-web
# Run /login inside Pi, then exit.
docker compose up -d
```

PowerShell:

```powershell
Copy-Item .env.docker.example .env
New-Item -ItemType Directory -Force .runtime\docker\data
New-Item -ItemType Directory -Force .runtime\docker\pi
New-Item -ItemType Directory -Force workspaces
docker compose build
docker compose run --rm pi-web node dist/index.js set-password
docker compose run --rm --entrypoint pi pi-web
# Run /login inside Pi, then exit.
docker compose up -d
```

| Host path | Container path | Purpose |
| --- | --- | --- |
| `.runtime/docker/data` | `/data` | Configuration, SQLite, themes, runtime state |
| `.runtime/docker/pi` | `/home/node/.pi` | Pi login and sessions |
| `workspaces` | `/home/pi` | Projects Pi is allowed to access |

Do not mount the Docker socket or credential directories under `/home/pi`.

Operations:

```bash
docker compose ps
docker compose logs -f pi-web
docker compose exec pi-web node dist/index.js doctor
docker compose restart pi-web
docker compose down
```

## Remote access

Docker publishes `127.0.0.1:8787` by default. The systemd configuration is
remote-friendly, but Pi Web does not terminate TLS or manage firewall rules.
Use a trusted private network, SSH tunnel, or HTTPS reverse proxy. Never expose
plain HTTP directly to an untrusted network.

When TLS terminates at a reverse proxy, configure trusted-proxy and secure
cookie behavior deliberately. Review the [security model](security-model.md).

## Updates and backups

Before upgrading, back up:

- Pi Web configuration and SQLite data;
- installed themes and uploaded backgrounds;
- Pi's own credentials and session directory.

For Docker this normally means `.runtime/docker/data` and
`.runtime/docker/pi`. Rebuild from a pinned checkout, run `doctor`, then start
the updated services. Keep the previous checkout or image available until the
health check and a real login/session smoke test pass.
