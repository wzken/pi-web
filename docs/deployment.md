# Deployment

Pi Web supports Linux systemd user services and a self-contained Docker
Compose deployment. Both approaches run as an ordinary user and keep runtime
state outside the repository.

## Credentials

Keep these four credential classes separate:

1. The Pi Web access key authenticates the browser. Only its scrypt hash is
   stored.
2. Provider credentials belong to Pi and must be configured for the same
   operating-system or container user.
3. Scheduler worker tokens are short-lived internal credentials generated by
   Pi Web. Operators do not create or persist them.
4. The Web Push VAPID private key is generated once and stored in the
   sessiond-owned SQLite database. It is never returned to browsers; only the
   public key is exposed to an authenticated Push subscription flow.

Do not place real credentials in `.env.example`, screenshots, logs, issues, or
commits.

## Linux user services

From a release checkout:

```bash
pnpm install --frozen-lockfile
pnpm build
pnpm pi-web install
pnpm pi-web doctor
```

The installer writes:

- `~/.config/pi-web/config.json`
- `~/.local/share/pi-web/pi-web.sqlite`
- `~/.local/share/pi-web/sessiond.sock`
- `~/.config/systemd/user/pi-web-sessiond.service`
- `~/.config/systemd/user/pi-web-server.service`

It never runs `sudo`. An administrator may enable lingering if the user
services must survive logout:

```bash
loginctl enable-linger "$USER"
```

Useful commands:

```bash
pnpm pi-web status
pnpm pi-web doctor
pnpm pi-web stop
pnpm pi-web restart
pnpm pi-web set-password
pnpm pi-web reset-key
pnpm pi-web uninstall
```

`stop`, `restart`, and `uninstall` ask the running sessiond to enter drain mode
before invoking systemd. They refuse while Pi workers are active. Use
`--force` only when intentionally interrupting those workers, for example:

```bash
pnpm pi-web restart --force
```

Forced service changes are audited and active sessions are marked interrupted
when sessiond stops. Package installation, removal, and update use the same
active-worker policy in the web interface. `uninstall` removes service units
but preserves configuration, databases, schedules, and Pi session references.

## Docker Compose

POSIX shell:

```bash
cp .env.docker.example .env
mkdir -p .runtime/docker/data .runtime/docker/pi .runtime/docker/workspaces
docker compose build
docker compose run --rm pi-web node dist/index.js set-password
docker compose run --rm --entrypoint pi pi-web
# Run /login inside Pi, then exit.
docker compose up -d
```

PowerShell:

```powershell
Copy-Item .env.docker.example .env
New-Item -ItemType Directory -Force .runtime\docker\data
New-Item -ItemType Directory -Force .runtime\docker\pi
New-Item -ItemType Directory -Force .runtime\docker\workspaces
docker compose build
docker compose run --rm pi-web node dist/index.js set-password
docker compose run --rm --entrypoint pi pi-web
# Run /login inside Pi, then exit.
docker compose up -d
```

| Host path | Container path | Purpose |
| --- | --- | --- |
| `.runtime/docker/data` | `/data` | Configuration, SQLite, themes, runtime state |
| `.runtime/docker/pi` | `/home/node/.pi` | Pi login and sessions |
| `.runtime/docker/workspaces` | `/home/pi` | Projects Pi is allowed to access |

Do not mount the Docker socket or credential directories under `/home/pi`.

Operations:

```bash
docker compose ps
docker compose logs -f pi-web
docker compose exec pi-web node dist/index.js doctor
docker compose restart pi-web
docker compose down
```

## Remote access

Docker publishes `127.0.0.1:8787` by default. The systemd configuration is
remote-friendly, but Pi Web does not terminate TLS or manage firewall rules.
Use a trusted private network, SSH tunnel, an existing Tailscale Serve HTTPS
endpoint, or an HTTPS reverse proxy. Never expose plain HTTP directly to an
untrusted network.

The Settings page reports the current origin, private LAN addresses, Tailscale
IP addresses, and an existing Tailscale Serve HTTPS address when the local
`tailscale` CLI reports one. It generates the QR code locally on the Pi Web
server. Detection is read-only: Pi Web never runs `tailscale serve`, changes a
firewall, opens a port, or publishes an address. Configure Tailscale or the
reverse proxy separately, then reload the Settings page.

Background Push requires a browser secure context: HTTPS, or a loopback origin
such as `http://127.0.0.1` during local development. A plain LAN URL such as
`http://192.168.x.x` can use the persistent in-app inbox but browsers will not
allow a Push subscription. Each device must opt in separately. Signing out
removes that device subscription; resetting the access key removes all
subscriptions transactionally.

When TLS terminates at a reverse proxy, set `PI_WEB_TRUSTED_PROXY=true` only if
the Pi Web port is reachable exclusively through that proxy; otherwise clients
can forge forwarding headers and bypass IP-based login throttling. Set
`PI_WEB_COOKIE_SECURE=always` for the proxied HTTPS origin. Review the
[security model](security-model.md).

## Updates and backups

Before upgrading, back up:

- Pi Web configuration and SQLite data, including notification history, VAPID
  keys, and active Push subscriptions;
- installed themes and uploaded backgrounds;
- Pi's own credentials and session directory.

Restoring SQLite also restores VAPID keys and subscription endpoints, but Push
services may have expired individual subscriptions while the backup was
offline. Stale HTTP 404/410 subscriptions are removed automatically after the
next delivery attempt. Restoring only configuration without SQLite creates a
new VAPID identity and requires every browser to subscribe again.

Close active sessions before changing Pi packages or restarting sessiond. For a
systemd checkout upgrade, back up first, then run:

```bash
git pull --ff-only && pnpm install --frozen-lockfile && pnpm build && pnpm pi-web restart && pnpm pi-web doctor
```

`pnpm pi-web restart` refuses to interrupt active workers unless `--force` is
provided. Pi Web requires Pi Coding Agent 0.84.1 or newer and `doctor` probes
its required no-model RPC command surface after the updated services start.

For Docker this normally means `.runtime/docker/data` and
`.runtime/docker/pi`. Docker Compose cannot use the host systemd drain command;
check the dashboard for active workers and close them before `docker compose
restart` or `down`. Rebuild from a pinned checkout, run `doctor`, then start the
updated services. Keep the previous checkout or image available until the
health check and a real login/session smoke test pass.
